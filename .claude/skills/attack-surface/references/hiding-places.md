# 見落とされやすい場所と探し方（パス 2 のレンズ）

パス 1 は「ファイルを順に読む」。パス 2 は逆に、**観点を 1 つ決めて全ソースを横断する**。
同じコードでも、見る角度が違えば別のものが見える。各レンズは独立に動かし、互いの結果もパス 1 の結果も見せない。

各レンズに挙げた検索語は **とっかかり** にすぎない。検索に掛かった所を読み、そこから芋づるで辿る。
知らないフレームワークなら、まずその仕組み（どうやって入口を登録するか）をコードから読み取ってから探す。
レンズに書かれていないことを見つけたら、それも記録する。

## 目次

1. `entry` — 入口から辿る
2. `implicit` — 書かれていないのに存在するもの
3. `client` — 呼ぶ側から逆引きする
4. `infra` — インフラと公開範囲
5. `nonhttp` — HTTP 以外の入口
6. `leftover` — 残置物と切り替え式
7. `authz` — 認証・認可の境界
8. `intake` — 受け口: 入口が実際に受け取っているもの
9. `parsers` — 解釈点: 値が解釈される場所を、解釈処理の側から探す
10. `assumptions` — 開発者の前提を破る
11. `open` — 自由枠

1〜7 は入口の層、8 は受け口の層、9 は解釈点の層を担当する。10 と 11 は層をまたいで盲点を探す。

入力の内容に合わせてレンズを足し引きしてよい（インフラ定義が 1 つも無ければ `infra` は軽く、モバイルアプリがあれば専用のレンズを足す、など）。
ただし `implicit`・`client`・`leftover`・`intake`・`parsers`・`assumptions`・`open` は、把握されていないものを見つける主力なので省かない。

---

## 1. `entry` — 入口から辿る

**狙い**: アプリの起動点から「何が登録されるか」を上から辿り、実際に生きている入口の全体を組み立てる。パス 1 が個々のファイルで見たものを、登録の連鎖として検証する。

- 各ソースの起動点を特定する（`main`、`index`、`app`、`server`、`Program`、`Application`、`wsgi` / `asgi`、`manage.py`、フレームワークの設定ファイル、`Dockerfile` の `CMD`、`package.json` の `scripts`、`Procfile`）
- そこから登録の連鎖を辿る: ルーターのマウント、モジュールの import、コントローラの登録、ミドルウェアの順序、プラグイン、サブアプリ
- **規約で自動登録される仕組み** を見落とさない: ファイル配置ベースのルーティング、コンポーネントスキャン、アノテーション / デコレータ / 属性での自動検出、オートロード、命名規約（`*Controller` の public メソッドが全部入口になる等）。この場合、置かれているだけで生きている
- ディスク上にあるのに連鎖に現れないハンドラ・コントローラを列挙する（死んでいるのか、別経路で登録されているのか）
- 複数の起動点（Web、ワーカー、管理用サーバ、別ポートの内部 API）がないか
- 公開パスの組み立て: ベースパス、コンテキストパス、バージョン接頭辞、リバースプロキシの書き換え

検索のとっかかり: `listen` `serve` `createServer` `run(` `bootstrap` `register` `mount` `use(` `include` `route` `router` `urlpatterns` `MapControllers` `@SpringBootApplication` `ComponentScan` `autoload`

## 2. `implicit` — 書かれていないのに存在するもの

**狙い**: 依存や設定を入れただけで生える入口。開発者のコードに現れないので、最も把握されていない。

- 全ソースの依存マニフェスト（`package.json`、`requirements*.txt`、`pyproject.toml`、`pom.xml`、`build.gradle`、`go.mod`、`Gemfile`、`composer.json`、`*.csproj`、`Cargo.toml`、`mix.exs`、`pubspec.yaml`）と、コンテナ定義のイメージ名を全部読む
- `RUN/work/knowledge.md` の「1. 暗黙に存在し得るエンドポイント」を読む（知識ベースから、この入力の依存・イメージ・記述に手がかりがあった項目を機械的に抜き出したもの）。
  載っている項目は 1 つ残らず確かめ、載せるか、無効と確かめて `dismissed` として報告する。載せる項目の `kb` 欄には見出しの ID を書く。
  知識ベース本体（[implicit-endpoints.json](implicit-endpoints.json)）は通読しない。抜粋に無い依存を調べるときだけ、依存名や ID で検索する
- **知識ベースは網羅ではない。** 載っていない依存についても、あなたの知識で「これは既定で何を公開するか」を考える。確信が無ければ `confidence: low` で載せ、実機で確かめる方法を `notes` に書く
- 設定で有無や場所が変わるものは設定を読む（ドキュメント UI の無効化、管理系エンドポイントの公開範囲、ベースパス、デバッグモード）
- フレームワーク本体の既定の振る舞い: 静的ファイルの既定配信、既定のエラーページ、自動で生える CRUD、開発サーバ専用の口、ソースマップ、`/.well-known/` 配下
- **フレームワークを使っていないシステムでは、実行基盤そのものが暗黙の口を生やす。** 公開ディレクトリに置かれたスクリプトの直接実行（ルーターを通らない）、
  起動用スクリプトへの追加のパス（`/index.php/任意` のような形）、既定の文書名、言語の内蔵サーバーの配信範囲、捕捉されない例外の既定の出力、デバッガの待ち受け。
  「依存にフレームワークが無いから暗黙の口は無い」と片付けない

特に見落とされやすい例（これに限らない）:
API ドキュメント UI と定義ファイル / 管理画面 / ヘルス・メトリクス・プロファイラ / 認証ライブラリが生やすログイン・コールバック・トークン系一式 /
Router に登録しただけで増える操作（ViewSet の追加アクション、リソースルートの 7 操作）/ リポジトリやエンティティを自動公開する仕組み /
ファイルの直接アップロード口 / 画像最適化・変換の口 / Server Actions のような「関数を書いただけで公開される」仕組み /
リアルタイム通信の既定パス / GraphQL の introspection と IDE / デバッグツールバー / import しただけで登録されるデバッグ用ハンドラ /
ジョブ管理 UI / 同梱ミドルウェアの管理コンソールと既定ポート

## 3. `client` — 呼ぶ側から逆引きする

**狙い**: 「呼ばれている先」をすべて集め、サーバ側の定義と突き合わせる材料を作る。受け側が入力に無ければ、渡されていないサービスが存在する証拠になる。

集める場所:

- フロントエンド: `fetch`、`axios` などの HTTP クライアント、API クライアント層、生成された SDK、GraphQL のクエリ文、フォームの `action`、`WebSocket` / `EventSource` の接続先
- ベース URL の解決: 環境変数（`.env*`）、設定ファイル、ビルド時定数。ベース URL と相対パスを結合して完全な宛先にする
- モバイル: API 定義（Retrofit 等のインタフェース、URL 定数）、ディープリンク定義
- サーバ間: 他サービスを呼ぶクライアント、SDK、キューへの送信先、Webhook の送信先
- テストコード: テストが叩いているパス（テストがあるのに本体に見当たらないパスは要注意）
- 文書・運用物: README や手順書の `curl` 例、Postman / Insomnia / `.http` ファイル、負荷試験の定義、OpenAPI
- ビルド済みの JS（ソースが無く成果物だけある場合）: 文字列として埋まっているパスや URL
- 文字列として現れる URL・ホスト名全般（設定、コメント、定数）
- **ホスト名を文字列から拾い切る**: 入力の全ファイル（開かない区分も）から `http://` `https://` `wss://` などで始まる文字列と、スキームの無いイメージ名・取得元（`ホスト名/名前/名前`）を検索し、ホスト名ごとに開いて確かめる。
  実行時にサーバーが接続する先、ブラウザの遷移先・読み込む資源、CI や開発用のコマンドの取得元、テストが実際に接続する先、このプロジェクトが運営する名前は、
  **1 ホスト 1 件**（kind `host`。`summary` にどれに当たるかと、どこに現れるか）。予約済み・例示用の名前（`example.com`、`*.invalid`、`*.test`）、XML の名前空間やスキーマの識別子、
  ライセンスや参考資料へのリンクは載せない。拾い漏れは `check.py` の 5d が挙げる

記録の仕方: 1 つの宛先（メソッド × パス、分かればホスト）を 1 件、`origin: client`（文書由来は `doc`、仕様由来は `spec`）。
`summary` に「どこから呼ばれているか」を書く。受け側がどのソースかの判定は手順 5 で行うので、ここでは集めることに徹する。

## 4. `infra` — インフラと公開範囲

**狙い**: 「実際に外から届くのは何か」。コードではなく配置の定義から露出点を拾う。

- コンテナ: `Dockerfile` の `EXPOSE` と起動コマンド（デバッグ用ポートやフラグ）、`docker-compose` の `ports`（`127.0.0.1:` 付きかどうかで公開範囲が変わる）、同梱しているイメージ
- オーケストレーション: Service の種類（外部公開か内部か）、Ingress / Gateway の経路とホスト、CronJob、プローブのパス（コードが無いサービスの入口が分かる）
- リバースプロキシ / ゲートウェイ: 経路ごとの転送先、接頭辞の書き換え、認証の有無、内部向け指定、ディレクトリ一覧、ステータス画面
- クラウド定義（Terraform、CloudFormation / SAM、Serverless Framework、CDK、Bicep など）: API Gateway の経路と認可設定、関数の公開 URL とトリガ、ロードバランサのリスナー、
  全開放のセキュリティグループ / ファイアウォール、公開バケットとそのポリシー、CDN、DNS レコード、外部公開の DB
- PaaS 設定（Vercel、Netlify、Firebase、Cloudflare、Fly、Render、Heroku、App Engine など）: rewrites / redirects / functions / cron、セキュリティルール（全員読み書き可になっていないか）
- CI/CD: 外部から起動できるトリガ、デプロイ先のホスト、公開される成果物。**ワークフローの定義ファイルは 1 つずつ開き、ファイルごとに 1 件**書く（契機、誰が契機を作れるか、ジョブの権限、参照している秘密の名前）。
  ジョブの間の受け渡しも見る: 外部の PR で動くジョブが作った成果物・キャッシュ・出力を、書き込み権限や秘密を持つ別のジョブ（別のワークフローの完了を契機に動くもの、後続のデプロイ）が読む関係。
  秘密や書き込みできる鍵を持ったまま、リポジトリのコードを実行する手順
- **リポジトリを読み書きする外部の仕組み**: リポジトリ直下とドットで始まるディレクトリの設定ファイルを 1 つずつ開き、どの外部の仕組みに向けた設定かを判断する
  （依存の自動更新、翻訳の同期、コード解析・整形のサービス、バッジ、AI 支援ツール向けの指示書）。名前から推測せず中身を読む。
  仕組みごとに、何を契機に動くか、何を読み、どこへ書き戻すか（プルリクエスト、コミット、翻訳ファイル）を記録する。
  とっかかり: `.github/dependabot.yml` `renovate.json` `crowdin.yml` `.codeclimate.yml` `.scrutinizer.yml` `.styleci.yml` `sonar-project.properties` `.gitlab-ci.yml` `.circleci/` `Jenkinsfile` `.travis.yml` `azure-pipelines.yml`
- **公開ディレクトリの範囲**: アプリの起動点が、公開ディレクトリとコードの置き場所を分けているか（起動用のスクリプトと同じ階層に、ライブラリ・設定・依存物・データのディレクトリが並んでいないか）。
  分かれていなければ、ディレクトリごとに遮断の設定の有無を挙げる。遮断の設定は特定の Web サーバーでしか効かない（`.htaccess` は Apache だけ。nginx や言語の内蔵サーバーは読まない）ので、
  効く条件を `notes` に書く。**スクリプトを URL で直接実行できる実行基盤**（PHP など）では、公開ディレクトリに置かれたスクリプトの全部が入口になる（テスト、ツール、依存物の中のものも）。
  **単位を揃える**: 公開ディレクトリの直下を一覧し、ディレクトリごとに 1 件（`GET /ディレクトリ名/{path*}`）、直下のファイルごとに 1 件（`GET /ファイル名`）。ドットで始まるものも飛ばさない。
  ディレクトリの中の個別のファイルは別件にせず、ディレクトリの項目の `notes` に書く（別件にするのは、サーバーの設定がそのファイルだけを別扱いにしているときと、
  リポジトリには無く動作中やテストで作られるファイルのときだけ）
- **配置の形ごとの中身の違い**: 公開ディレクトリに何が置かれるかを、配置の形ごとに挙げる（リポジトリを取得してそのまま置く、リリース用アーカイブを展開する、コンテナイメージ）。
  `.gitattributes` の `export-ignore`、`.dockerignore`、`.npmignore`、依存定義の `files` 欄、イメージの `COPY` を読み、テスト・文書・開発用の設定・`.git` が配置に入るかを事実として書く。
  導入手順の文書に書かれた構成例・イメージ名・コマンド例も手がかりにする（定義が別のリポジトリにあれば、入力に無い旨を `SHADOW` で載せる）
- **実行時・開発時に公開ディレクトリの中へ生成されるもの**: データ、DB のファイル、ログ、キャッシュ、テストのカバレッジ報告、生成された API 文書、依存のディレクトリ。
  どの設定・コマンド（`Makefile`、依存定義の `scripts`、テスト設定の出力先、保存先の既定値）が、どこに何を作るかを読む。保存先の種類ごとに、遮断のファイルを作る処理があるかも見る。
  **書き込む処理から逆向きに探す**（`file_put_contents` `fopen` `rename` `copy` `mkdir`、シェルの `>` `cp` `mv` `ln`、各ツールの出力先の設定）。
  作られるディレクトリは 1 件、その中に作られるファイルは**種類ごとに 1 件**（名前の決まり方を path に、PHP として実行される名前か・そのまま返る名前か、中身を `summary` に）
- **除外設定に挙がっている名前**: `.gitignore` `.dockerignore` などの各行を読み、リポジトリには無いが配置先にはあり得るもの（運用者が置くファイル、ツールや IDE が作るもの、テストの出力）を挙げる。
  公開ディレクトリの中に置かれ得るなら、静的配信として 1 件ずつ（`confidence: low`、どの行に挙がっているかを根拠に）
- 設定・環境ファイルに現れるホスト名、ポート、接続先（値に資格情報が含まれていたら伏せる）

各露出点について「誰から届くか」（インターネット / 同一ネットワーク / ホスト内のみ）を、定義から読み取れる範囲で書く。

## 5. `nonhttp` — HTTP 以外の入口

**狙い**: リクエスト / レスポンスの形をしていない入口。ルート一覧には現れない。

- WebSocket / SSE / Socket.IO / SignalR / Action Cable / Channels / LiveView: 接続口と、受信するイベント・メッセージ種別ごとのハンドラ
- GraphQL: スキーマの全フィールド（クエリ・ミューテーション・サブスクリプション）。コードファーストならリゾルバ定義から
- gRPC / Thrift / 独自 RPC: サービスとメソッド、`.proto`
- メッセージング: キュー・トピック・ストリームの購読者（誰が書き込めるか）、タスクキューのタスク
- 定期実行: cron、スケジューラ、バッチ。**外部から取ってきたデータを処理するもの** は入口
- イベント起動: ストレージ配置、DB の変更、メール受信、認証イベント
- ファイル取り込み: インポート機能、アップロード後の非同期処理、監視ディレクトリ
- コマンド: 管理コマンド、運用スクリプト（引数や環境変数が外部由来になり得るもの）。`Makefile` のターゲットと、依存定義の `scripts` も、ターゲットごとに 1 件。
  識別子は、スクリプトならソースのルートからのパス（`bin/administration`）、ターゲットなら `make ターゲット名`・`npm run 名前`（パス 1 の読み手も同じ単位・同じ書き方で書く）
- クライアント側: ディープリンク、URL スキーム、Intent、`postMessage`、IPC、WebView ブリッジ、ブラウザ拡張。
  ブラウザの画面では、URL のクエリとフラグメント、ドラッグ＆ドロップ、クリップボードからの貼り付け、ファイル選択、`localStorage` などの保存領域、サーバーの応答も入力になる
- **サーバーが中身を見ない設計**（ブラウザ側で暗号化・復号する、署名済みのデータをそのまま中継する）では、保存した人の値を解釈するのは別の利用者のクライアント。
  サーバー側のハンドラを読んでも解釈処理は出てこないので、クライアント側のコードを、復号・復元の後に値がどこへ流れるかで辿る
- 生のソケット: TCP / UDP の待ち受け、独自プロトコル

## 6. `leftover` — 残置物と切り替え式

**狙い**: 本番にあるはずがないと思われている入口。開発者の記憶から消えているもの。

- 名前で探す: `debug` `test` `tmp` `temp` `dev` `old` `backup` `bak` `sample` `example` `demo` `mock` `stub` `poc` `legacy` `deprecated` `internal` `hidden` `secret` `hoge` `fuga`（パス・ファイル名・関数名・ルート名の両方で）
- 条件付きで生きる入口: 環境変数・デバッグフラグ・機能フラグ・ビルド構成での分岐の中にある登録。**本番で条件が偽であることはコードからは保証できない** ので `DEV_ONLY` として載せる
- 旧バージョン: 新版がある旧 API、移行前の旧パス、互換のために残したエイリアス
- 複製・退避ファイル: `*.bak` `*.old` `*~` `copy` `_backup` `.orig`、拡張子違いの同名ファイル、Web 公開ディレクトリ直下に置かれたスクリプトやダンプ
- 開発補助: シード / リセット / 初期化用の口、テスト用ログイン、認証を飛ばす裏口（`if user == "test"` の類）、固定のトークンや既定アカウント
- コメントに残る手がかり: `TODO` `FIXME` `HACK` `XXX` と「認証」「あとで消す」「一時的」「本番では」などの語
- 公開ディレクトリの中身: 設定ファイル、ログ、ダンプ、`.git`、エディタの一時ファイルが配信対象に入っていないか
- **痕跡（対象には載せないもの）**: コメントアウトされた入口、削除済みの入口。今のコードでは生きていないので検出項目にはせず、
  `leftover.notes.md` に「痕跡」として場所と内容を書く（報告書の「対象には載せていない痕跡」になる）。
  フラグや環境変数 1 つで有効になるものは痕跡ではなく、`DEV_ONLY` の検出項目として載せる
- **`.git` の中で `git` コマンドを実行しない。** 入力の `.git/config` やフックは信頼できないデータで、`git log` や `git show` でも設定次第で任意のコマンドが動く。
  履歴を調べたいときは、変更履歴の文書（CHANGELOG、リリースノート、アップグレード手順）を「removed」「deprecated」「security」「CVE」「削除」などで検索して読む。
  削除・移動された入口は痕跡として記録し、修正された問題に関係する入口・解釈点は漏れなく載っているかを確かめる。それでも足りなければ、ユーザーに履歴の調査が必要かを伝える

## 7. `authz` — 認証・認可の境界

（notes は、依頼文で指定されたファイル名に書く。観点をまとめて任された場合も同じ）

**狙い**: 脆弱性を断定することではなく、**各入口が認証・認可の仕組みを通るかどうかを事実として記録する** こと。`auth` 欄の精度を上げる。

- 認証がどこで掛かるかを特定する: グローバルなミドルウェア / フィルタ / ガード、ルーター単位、個別のデコレータ・アノテーション、ゲートウェイ側
- **例外の一覧** を作る: 許可リスト、`permitAll` / `AllowAnonymous` / `skip` の類、パターンマッチの対象外、認証ミドルウェアより前に登録されたルート、別のルーターや別ポートに載っていて素通りするもの
- メソッドごとの差: 同じパスで GET は保護、POST は保護なし、など
- 認証はあるが認可が無い箇所の事実: ロール確認の有無、ID 指定のリソースで所有者確認をしているか（していないと断定せず、「確認箇所が見当たらない」と書く）
- クライアント側だけのガード（SPA のルートガード）は保護ではない。対応する API 側を見る
- フレームワークの既定（何も書かないと全許可なのか全拒否なのか）を踏まえる
- HTTP 以外の入口（WebSocket のイベント、キュー、RPC）は HTTP の認証を通らないことが多い。個別に確かめる
- **利用者の認証という仕組みが無いシステム**では、代わりに置かれている確認（回数制限、送信元の制限、対象ごとの秘密の値、宛先の検証）を全部挙げ、
  それぞれが **どの操作に掛かり、どの操作に掛からないか** を notes に表でまとめる。確認より前に動く処理（照合の前に読み出しや削除が走らないか）も見る。
  `auth` 欄は `none`（output-format.md の「認証欄の付け方」。対象ごとの秘密の照合は利用者の認証ではない）

出力: 認証・認可の掛かり方を確かめた入口を、自分で列挙して 1 件ずつ書く（他の担当者の一覧は見ないので、対象の入口は自分で見つける）。
`auth` / `auth_evidence` を、[output-format.md](output-format.md) の「認証欄の付け方」に従って埋める。同じ入口を別の担当者も記録していれば、統合時に 1 件にまとまり、
証拠のある判断が採られる（判断が食い違えば `AUTH_CONFLICT` が付いて人が決める）。全入口を網羅する必要はないが、**例外・抜け・ばらつきのある所は必ず** 書く。
notes（依頼文で指定されたファイル）に、認証の仕組みの全体像（どこで掛かり、何が例外か）をソースごとにまとめる。

## 8. `intake` — 受け口: 入口が実際に受け取っているもの

**狙い**: 開発者が読むコードを書いていないのに、基盤が受け取り、処理に使っている入力を挙げる。ルートの一覧には絶対に現れない層。
手がかりは [intake-catalog.md](intake-catalog.md) の A・B・C・E・F と、`RUN/work/knowledge.md` の「2. 受け取り・解釈を担う部品」のうち層が「受け口」のもの
（知識ベース [parser-components.json](parser-components.json) からの抜粋。載っている部品は全部確かめ、載せるか `dismissed` として報告する）。
受け口か解釈点かで迷うものは、output-format.md の「受け口か解釈点か」で決める（同じ仕組みを両方に書かない）。

- **ソースごとに、リクエストがハンドラに届くまでの道筋を全部読む**: サーバ／コンテナの設定、フレームワークの設定、ミドルウェア・フィルタ・インターセプタ・プラグインの登録と順序。
  それぞれについて「何を読むか、どう解釈するか、どのルートに掛かるか、認証より前か後か」を書く
- **受ける形式を確かめる**: 本文の Content-Type（JSON のつもりの口が、フォーム・multipart・XML・テキストも受けないか）、クエリ・フォームの入れ子や配列、
  アップロードを受ける範囲、圧縮、文字コード。既定で有効なものは、開発者が設定していなくても載せる
- **信頼しているヘッダを挙げる**: プロキシ由来（転送元 IP・ホスト・スキーム）、メソッドやパスの上書き、内部用・デバッグ用のヘッダ、認証情報を運ぶもの全部。
  そのヘッダの値が何に使われるか（アクセス制御、レート制限、URL 生成、ログ）まで追う
- **Cookie・セッション・トークン**: 復元の方式（単なる署名か、オブジェクトの復元か）、鍵の出どころ、読み取り経路が複数ないか
- **フレームワーク独自の通信経路**: サーバ側の関数やコンポーネントをクライアントから呼ぶ仕組み、状態の送り返し、ページ用データの別経路、RPC のバッチ。
  **利用者定義のハンドラが無くても、仕組みが有効なら載せる**
- **自動バインド・自動クエリ**: リクエストからオブジェクトへ名前で値が入る箇所と、入り得る項目の範囲。クエリ文字列で検索・絞り込み・並び替え・関連の展開ができる範囲
- **フレームワーク・主要部品のバージョン** を依存定義から読み、`component` に書く。その版に既知の重大な問題があったと記憶していれば、
  「記憶に基づく・要確認」と明記して `notes` に添える（外部に問い合わせて確かめることはしない）

記録: `kind: input-channel`。1 つの仕組みを 1 件。掛かる範囲を `scope`、受け取るものを `consumes` に書く。開発者のコードが読んでいない入力なら `UNINTENDED_INTAKE`。

## 9. `parsers` — 解釈点: 値が解釈される場所を、解釈処理の側から探す

**狙い**: 入口から辿る読み方では、ジョブ・コールバック・ライブラリ内部・別サービスにある解釈処理に届かない。逆に、**解釈処理を全部見つけてから、誰が値を届けられるかを遡る**。
手がかりは [intake-catalog.md](intake-catalog.md) の D と「追い方」、`RUN/work/knowledge.md` の「2. 受け取り・解釈を担う部品」のうち層が「解釈点」のもの
（載っている部品は全部確かめ、載せるか `dismissed` として報告する）。フレームワークがコードの前に行う復元（本文パーサ、Server Action の引数、セッション）は
`intake` の担当なので、ここでは書かない（output-format.md の「受け口か解釈点か」）。

- **依存定義に現れない解釈器を探す**: コマンドとして呼ばれる外部ツール（ExifTool、ImageMagick、FFmpeg、Ghostscript、LibreOffice、wkhtmltopdf、pandoc など。
  `exec` `spawn` `subprocess` `system` の引数、Dockerfile の `apt-get install` / `apk add`）、別コンテナの変換サービス（compose のイメージ名と、そこへ送っている行）、自前で書かれたパーサ

- **依存から**: 全ソースの依存定義を読み、解釈を担う部品（デシリアライズ、XML、YAML、テンプレート、式、画像・動画・文書、アーカイブ、表計算、メール、Markdown、SAML・JWT など）を挙げる。
  部品ごとに、コード中の使用箇所を全部探す
- **コードから**: 標準ライブラリや言語機能による解釈（直列化の復元、`eval` 相当、外部コマンド、動的なクラス・メソッド解決、文字列からのテンプレート、生のクエリ、入力を含むパスや URL）を検索する。
  知識ベースに無い部品も、名前と使われ方から判断する
- **見つけた解釈処理ごとに遡る**: その入力はどこから来るか。リクエストから直接か。保存された値か（誰が保存できるか）。他のサービス・キュー・ファイル・外部 API からか。設定からか（設定は誰が変えられるか）
- **自動で走る解析を探す**: アップロード後の処理（サムネイル、メタデータ、検査、索引、変換）、受信メール、取り込み、プレビュー取得、通知・帳票の生成、エクスポート、バックアップと復元
- **保存や中継を挟む流れ**（[surface-taxonomy.md](surface-taxonomy.md) の 15）を必ず見る。入口と解釈点が別のファイル・別のソースにあるものが、最も見落とされる
- **開かない区分のファイルでも、実行時にアプリが読み込んで解釈するもの**（翻訳・文言の定義、データとして読み込むテンプレートや設定）は、検索で中身の形を確かめる。
  書式の指定（`%s` `%1$s` `{0}`）、HTML のタグ、スクリプトの断片がどのくらいあるか、それを読み込んで解釈する行はどこか。外部から中身が届く経路（翻訳の同期サービス、管理画面からの編集）があれば、その入口を `fed_by` に書く。
  確かめた範囲（何を検索し、何件当たったか）を notes に書く
- 届く経路が確定できなくても載せる。「このパーサには信頼できるデータしか来ない」は確認すべき主張であって、除外の理由ではない

記録: `kind: parser`。解釈を行う箇所ごとに 1 件。根拠の 1 件目は **解釈を行うその呼び出しの行** にする（別の人が同じ箇所を見つけたとき突き合わせるため）。
`parses`（何を）、`component`（何で。バージョンも）、`fed_by`（どの入口から）、`reach`（`direct` / `indirect` / `unknown`）を埋める。

## 10. `assumptions` — 開発者の前提を破る

**狙い**: コードには、書き手の前提が埋まっている。攻撃はその前提が成り立たない場所で起きる。前提を言葉にして並べ、**それを破る入力経路が実在するか** を調べる。

前提の見つけ方: コメント（「内部用」「ここには来ない」「検証済み」「信頼できる」）、命名（`internal` `private` `trusted` `safe` `raw` `unsafe` `admin` `system`）、
検証の非対称（ある経路では検証し、同じ処理に届く別の経路ではしていない）、型や形式の決め打ち、エラー処理の欠落、認証の掛け方のばらつき。

よくある前提と、確かめること:

| 前提 | 確かめること |
|---|---|
| 「これは自社のフロントからしか呼ばれない」 | フロントが送らない項目・形式・順序で呼べる。フロント側の検証は存在しないのと同じ |
| 「このヘッダはプロキシが付ける」 | クライアントが同じヘッダを送ったとき、上書きされるか、そのまま通るか。プロキシを通らない経路（別ポート、内部ネットワーク、直接公開）は無いか |
| 「内部 API なので認証は不要」 | その API に届く経路: ゲートウェイの設定漏れ、同居する別サービスからの到達、利用者の入力で宛先を決める通信機能 |
| 「この ID は推測できない」「この URL は知られない」 | ID・URL が出力・ログ・リファラ・他の応答に現れる場所。連番や時刻由来でないか |
| 「この値はサーバが決めたもの」 | クライアントに一度渡して送り返させている値（隠し項目、状態、署名なしのトークン、価格、権限） |
| 「DB・キャッシュ・キューの中身は信頼できる」 | そこに書き込める経路を全部挙げる。別サービス、インポート、管理機能、過去のバージョン |
| 「管理者しか使わない」 | 管理者に届く入力（一般利用者が保存した値を管理画面が解釈する）。管理機能の認可が UI の非表示だけでないか |
| 「この形式しか来ない」 | 別の Content-Type、別の文字コード、入れ子・配列・巨大な値、重複したパラメータ、欠けた項目 |
| 「この順番でしか呼ばれない」 | 手順を飛ばす、繰り返す、並行させる、別の利用者の途中状態に割り込む |
| 「テナント・利用者は分離されている」 | 分離の根拠が毎回のクエリ条件なのか、どこかで一度確認しただけなのか。共有されているキャッシュ・ファイル置き場・キュー |
| 「開発・検証用で本番には無い」 | 有効・無効を決める条件と、その条件を外から変えられる可能性 |

出力: 前提ごとに、破れる経路が見つかれば該当の入口・受け口・解釈点として載せる（既存の項目と同じものなら、`notes` に前提と破れ方を書いた行を出す。統合時に合算される）。
notes（依頼文で指定されたファイル。観点をまとめて任された場合は、そのまとめた名前のファイル）に「見つけた前提の一覧」と、それぞれ破れる経路があったか・無かったか・不明かを残す。

## 11. `open` — 自由枠

**狙い**: 上のレンズ自体が持つ盲点を補う。観点を与えられると、その観点の外を見なくなるため。

指示は最小限にする: 「このシステムに外部から入力を届ける方法を、常識的な一覧に載らなさそうなものを中心に探せ」。
ヒントとして渡すのは `orientation.md` と [surface-taxonomy.md](surface-taxonomy.md) だけ。他のレンズの説明は渡さない。

考える切り口の例（縛りではない）: この業種・この種のシステムなら当然あるはずの機能が、ここまでの一覧に対応するコードとして存在するか /
データはどこから入ってどこへ出るか / 運用者は何を使って管理しているか / 取引先や他システムとどうつながっているか /
このコードを書いた人が「ここは外からは来ない」と思い込んでいそうな箇所はどこか。
