# 何をアタックサーフェスとみなすか

判断基準は 1 つ: **外部の誰か・何かが、このシステムに入力を届けられる経路か**。
「外部」には、インターネット上の匿名の第三者だけでなく、ログイン済みの一般ユーザー、取引先のシステム、同じネットワークの別サービス、
アップロードされたファイル、キューに積まれたメッセージ、開発者の端末も含む。到達できる相手が限られていても載せ、誰が届けられるのかを書く。

下の分類は **最低限拾うもの**。ここに無い種類を見つけたら `kind: other` で載せる。分類に当てはめることより、載せることが大事。

## 3 つの層

列挙するのは「エンドポイントの一覧」だけではない。次の 3 層をそれぞれ挙げ、つなぐ。

| 層 | 問い | 種別 |
|---|---|---|
| **入口**（経路） | どこに届くか | 下の 1〜12 |
| **受け口**（入力チャネル） | その入口は、開発者が読んでいるつもりの項目以外に **何を** 受け取るか | 13（`input-channel`） |
| **解釈点**（パーサ） | 受け取った値は **どの処理に** 解釈されるか | 14（`parser`） |

入口の層は「開発者が作ったもの」と「フレームワークが生やしたもの」で大半を拾える。
受け口と解釈点の層は、**開発者が意識していないことのほうが多い**。フレームワーク・ミドルウェア・ライブラリ・実行基盤が勝手に行っているからで、
近年の重大な脆弱性の多くはこの層にある。ここを挙げるかどうかが、攻撃者より広く見えているかどうかの分かれ目になる。

## 1. HTTP で呼べるもの (`http` / `page` / `static`)

- API のエンドポイント（メソッドとパスの組ごとに 1 件）
- 画面（サーバが返すページ、フォームの送信先）
- 静的ファイルの配信、アップロード先とダウンロード元、ユーザーがアップロードしたファイルの公開パス
- リダイレクタ、エラーハンドラ、フォールバック（`/*` で受けるもの）、プロキシとして転送するパス
- 同じ機能の旧バージョン（`/v1/…` と `/v2/…` は別件として両方）

記録するのは **外から見える完全なパス**。ルーターのマウント、ベースパス、ゲートウェイでの書き換えを辿って組み立てる。

## 2. HTTP の上の別プロトコル (`websocket` / `graphql` / `grpc` / `rpc`)

- WebSocket・SSE・Socket.IO: 接続先と、受け付けるイベント / メッセージ種別ごと
- GraphQL: エンドポイントと、クエリ・ミューテーション・サブスクリプションの各フィールド
- gRPC・Connect・Twirp・tRPC・JSON-RPC・SOAP: サービスとメソッドごと
- フレームワーク固有の RPC: Next.js の Server Actions、Livewire、Blazor、Phoenix LiveView のイベントなど。
  画面のボタンに見えても実体は誰でも直接呼べる入口

## 3. 書かれていないのに存在するもの（暗黙）

フレームワーク・ライブラリ・ミドルウェア・コンテナイメージが、設定や依存を入れただけで生やすエンドポイント。
開発者のコードには現れないので把握されていないことが多い。API ドキュメント UI、管理画面、ヘルスチェック、メトリクス、
デバッグ用の口、認証ライブラリのコールバック、ファイルアップロードの既定ルートなど。→ [hiding-places.md](hiding-places.md) のレンズ 2

## 4. 管理・運用・デバッグ用の口

管理画面、ジョブ / キューの管理 UI、DB 管理ツール、API ドキュメント、プロファイラ、デバッグコンソール、機能フラグの切替口、
メンテナンス用 API、シード / リセット用の口。「社内向け」「開発中だけ」のつもりで作られ、公開範囲の確認が抜けやすい。

## 5. 認証・ID に関わる口

ログイン、ログアウト、登録、パスワード再設定、メール確認、招待、多要素認証、トークン発行 / 更新 / 失効、
OAuth / OIDC / SAML のコールバックとメタデータ、API キーの発行、セッション管理、なりすまし（impersonate）機能。
認証の「外側」に置かれる口なので、必ず個別に列挙する。

## 6. 外から届く非同期の入力 (`event` / `job`)

- Webhook（決済、チャット、メール配信、CI など外部サービスからの通知）
- メール受信、SMS 受信
- メッセージキュー / トピックの購読、ストレージイベント（バケットへの配置で起動する処理）
- 定期実行ジョブが **取りに行く** 外部データ（フィード、取引先のファイル、スクレイピング）
- ファイル取り込み（CSV / Excel / XML / 画像 / アーカイブのインポート）

HTTP の口が無くても、処理されるデータを外部が用意できるなら対象。何を契機に、誰が置いたデータを読むのかを書く。

## 7. インフラ上の露出 (`port` / `proxy` / `cloud` / `host`)

- 公開されるポート（コンテナ、VM、セキュリティグループ、ファイアウォール）。DB・キャッシュ・デバッガのポートは特に
- ロードバランサ、Ingress、リバースプロキシ、API Gateway の経路。どのパスがどこへ流れるか
- サーバレス関数の公開 URL、関数のトリガ
- ストレージバケット、CDN、DNS レコード、証明書に載っているホスト名
- コードや設定に現れるホスト名（特に検証・開発・管理用: `stg-`, `dev-`, `admin.` など）
- 同梱されているミドルウェアや管理コンソール（コンテナ定義のイメージ名から分かるもの）
- CI/CD: 外部から起動できるワークフロー、デプロイ先、成果物の公開場所
- リポジトリを読み書きする外部の仕組み（依存の自動更新、翻訳の同期、コード解析・整形のサービス、AI 支援ツール）。それぞれが届けるコード・データ・設定と、書き戻す先
- 公開ディレクトリに置かれるもの・実行時や開発時に生成されるもの（設定、データ、DB のファイル、ログ、テスト、文書、依存物、カバレッジ報告）。
  スクリプトを URL で直接実行できる実行基盤では、置かれているだけで入口になる。遮断の設定があっても、特定の Web サーバーでしか効かないものは「効く条件」つきで載せる
- 配置の形（リポジトリを取得してそのまま置く / リリース用アーカイブ / コンテナイメージ）と、形ごとに公開ディレクトリへ入るものの違い

## 8. クライアント側にある入口 (`page` / `ipc`)

- SPA のルート（URL を直接打てば開ける画面。メニューに無い隠し画面を含む）
- モバイルアプリ: ディープリンク、URL スキーム、Intent / エクスポートされたコンポーネント、WebView の JavaScript ブリッジ、プッシュ通知のペイロード処理
- ブラウザ: `postMessage` の受信、Service Worker、ブラウザ拡張のメッセージ、URL のクエリとフラグメント、ドラッグ＆ドロップ・貼り付け・ファイル選択で入るファイル、
  `localStorage` などの保存領域、サーバーや外部サービスから返ってくる応答
- デスクトップ: Electron の IPC、カスタムプロトコル、ローカルで待ち受けるポート

## 9. サービス間・外部連携

- 内部 API（「内部からしか呼ばれない」前提のもの。前提が崩れると無防備）
- このシステムが **呼び出す** 外部の宛先。宛先の一覧そのもの（信頼している相手）と、宛先をリクエストから組み立てている箇所（SSRF の入口）
- 共有している認証基盤、データストア、キュー（片方のソースから書いたものをもう片方が読む関係）

## 10. データとして入ってくるもの (`file-input`)

アップロードされたファイルを解釈する処理（画像変換、文書変換、アーカイブ展開、XML / YAML / シリアライズ形式の読み込み）、
テンプレートに流し込まれる入力、インポート機能。入口のエンドポイントとは別に、「何の形式を、どのライブラリで読むか」を備考に書く。

## 11. 人と運用を経由するもの (`cli` / `other`)

管理コマンド、マイグレーション、シードデータ（既定アカウントや初期パスワードを作るもの）、運用スクリプト、
設定ファイルやリポジトリに残っている資格情報（**値は写さず、場所と種類だけ**）。

## 12. その他 (`other`)

上のどれでもないが、基準に当てはまるもの。例: 独自プロトコルのソケット、ゲームサーバの UDP、IoT のトピック、
プラグイン機構、LLM に渡されるユーザー入力とそこから呼ばれるツール、他テナントから届く共有データ。

## 13. 受け口 — 入口が実際に受け取っているもの (`input-channel`)

ハンドラのコードが読んでいる項目だけが入力ではない。ハンドラの手前と外側で、基盤が受け取り、解釈しているものを挙げる。
探し方は [intake-catalog.md](intake-catalog.md) の A〜C。

- **全ルート共通の処理**: 本文の解釈（どの形式を受けるか）、クエリやフォームの構文（入れ子・配列・型変換）、ファイルアップロードの受け付け範囲、
  Cookie・セッションの復元、認証情報の読み取り経路、プロキシ由来ヘッダの信頼、メソッドやパスの上書き、形式の切り替え
- **フレームワーク独自の通信経路**: サーバ側の関数・コンポーネントをクライアントから呼ぶ仕組み、状態の送り返しと復元、ページ用データの別経路、RPC のバッチ
- **自動バインド・自動クエリ**: 名前の一致だけでオブジェクトの項目に値が入る仕組み、クエリ文字列から任意の属性を検索・並び替えできる仕組み
- **手前の層**: リバースプロキシ・ゲートウェイ・CDN・サーバレス基盤が解釈する項目、アプリとの解釈の食い違いが起きる箇所

「開発者はこの入力を読むコードを書いていないが、基盤が受け取って処理に使っている」ものには `UNINTENDED_INTAKE` を付ける。
ユーザー定義のハンドラが 0 件でも、仕組みが有効なら経路は存在する。ハンドラの有無ではなく仕組みの有無で判断する。

## 14. 解釈点 — 受け取った値が解釈される場所 (`parser`)

値を「データとして保存・表示する」だけの処理ではなく、**構造や命令として解釈する** 処理。探し方は [intake-catalog.md](intake-catalog.md) の D。

デシリアライズ、XML、YAML、テンプレート、式言語、動的なコード実行、外部コマンド、クエリの組み立て（SQL・NoSQL・LDAP・検索）、
画像・動画・文書の解析と変換、HTML からの PDF／画像生成、アーカイブ展開、CSV・表計算、Markdown・HTML の整形、メールの解釈、
入力から組み立てた宛先への通信、入力を含むパスでのファイル操作、認証トークンの検証、入力から作る正規表現。

各解釈点について書くこと:

- **何を、どの部品で** 解釈するか（部品名とバージョン。バージョンが分かれば、診断側で既知の問題を調べられる）
- **どこから届くか**（`fed_by`）: 入口を挙げる。直接か、保存・中継を経てか（`reach`）。辿れなければ「不明」と書いて `REACH_UNKNOWN`
- **認証の手前か後か**: 認証・認可より前に動く解釈処理は、誰でも到達できる。フラグ `PRE_AUTH` を付ける

届く経路が見つからない解釈点も載せる。「外からは届かない」は書き手の前提であって、確認された事実ではない。

## 15. 間接的に届く入力（保存・中継されてから解釈されるもの）

入口で受け取った値が、その場では解釈されず、**後で、別の場所で** 解釈されるもの。入口のハンドラを読むだけでは見えない。`SECOND_ORDER` を付ける。

- 保存されたファイルが、ジョブ・定期処理・別サービスで解析・変換される（サムネイル、メタデータ抽出、ウイルス検査、全文索引、文書変換）
- 保存された文字列が、後でテンプレート・コマンド・クエリ・URL・ファイルパスに使われる（通知メール、帳票、エクスポート、Webhook 送信先、バックアップ）
- あるソースが書いたものを別のソースが読む（キュー、共有 DB、キャッシュ、共有ストレージ）。読む側は「内部のデータ」として信頼していることが多い
- 外部サービス経由で届く値（OAuth のプロフィール項目、Webhook の中身、フェデレーション相手のデータ、取り込んだフィード、メールのヘッダ、ファイル名、メタデータ）
- 記録されてから管理者の画面やログ基盤で表示・解釈される値（User-Agent、Referer、エラーメッセージ、監査ログ）
- サーバーが中身を見ずに保存・中継する値（ブラウザ側で暗号化したデータなど）。解釈するのは、後でそれを受け取る別の利用者のクライアントで、解釈点はすべてクライアント側のコードにある
- リポジトリに届いてから本体に取り込まれる値（外部の翻訳者が書いた訳文、外部の PR が作った成果物、自動更新された依存）。取り込んだ後に、テンプレート・書式文字列・生成されるコードとして解釈される

## 1 件の単位

- **HTTP**: メソッド × パスで 1 件。同じパスの GET と POST は別件
- **RPC / GraphQL / WebSocket**: 操作（メソッド、フィールド、イベント）ごとに 1 件。エンドポイントそのものも 1 件
- **インフラ**: 露出点ごと（ポート、プロキシ経路、バケット、ホスト名）
- **受け口**: 仕組みごとに 1 件（ルートごとには増やさない）。どの範囲のルートに掛かるか（全体 / 接頭辞 / 個別）を `scope` に書く
- **解釈点**: 解釈を行う箇所ごとに 1 件（同じ部品でも、呼び出している場所が違えば別件）。届く入口は `fed_by` にまとめる
- **まとめて 1 件にしてよいもの**: 同じ仕組みで機械的に増えるもの（静的配信ディレクトリ配下、ワイルドカードで受けるプロキシ経路）。
  その場合はパスを `/static/{path*}` のように書き、何が配下にあるかを備考に書く。ただし CRUD を「一式」と丸めてはいけない。操作ごとに権限が違う
- **公開ディレクトリの静的配信**: 直下のディレクトリごとに 1 件、直下のファイルごとに 1 件。中の個別のファイルは原則として別件にしない（output-format.md の「数え方が割れやすいもの」）
- **コマンド・タスクの定義**: コマンドごと、ターゲットごとに 1 件（`Makefile` や依存定義の `scripts` を、ファイル全体で 1 件にしない）

## 載せるか迷ったとき

- テストコード内のサーバ、モック、サンプルアプリ → 載せる（`tags: ["in-test"]`）。本番に同梱される例がある
- コメントアウトされた入口、削除済みの入口 → 対象には載せない。「痕跡」として場所を記録し、報告書にまとめる（稼働中の版に残っていないかを確かめる材料）。
  フラグや環境変数 1 つで有効になるものは痕跡ではなく、`DEV_ONLY` として載せる
- フレームワークの規約上、入口にならないと確かめられたファイル（ルーティング対象外の置き場所など）→ 載せない。確かめた根拠を読了記録の `note` に書く。
  確かめられなければ `confidence: low` で載せる
- 依存にはあるが、有効にするための記述（ルートファイル、初期化、設定）が入力に見当たらないもの → 入れただけで有効になる仕組みなら載せる。
  明示的な組み込みが要る仕組みなら載せず、「入力から漏れている可能性」として網羅状況に書く。別の箇所がそれを参照している（設定がその URL を指している等）なら、
  受け側の無い呼び出し（`SHADOW`）として載せる
- 定義はあるが到達経路が見つからないコントローラ → 載せる（`confidence: low`）。自動スキャンで登録される仕組みかもしれない
- 依存ライブラリ（`node_modules` 等）の中身 → 個別には載せない。そのライブラリが生やす口は「暗黙」として、そのライブラリが担う受け取り・解釈は受け口・解釈点として載せる
- 解釈処理はあるが、外部の値が届くか分からない → 載せる（`REACH_UNKNOWN`、`confidence: low`）。届かないと確かめられたものだけ外す
- 管理者しか使えない機能の中の解釈処理 → 載せる。管理者の入力も入力であり、管理者に届く入力（保存された値の表示など）も経路になる
- 検証やサニタイズをしている入力 → 載せる。検証の有無は `notes` に書く。対象から外す理由にはならない
