# 受け口とパース点の手がかり集

エンドポイント（経路）を全部挙げても、アタックサーフェスの列挙は終わらない。
実際に攻撃されるのは「値を受け取って解釈する処理」であり、その多くは **開発者が書いていない**。
フレームワーク、ミドルウェア、ライブラリ、実行基盤が、開発者の意図と無関係に入力を受け取り、解釈している。

- React Server Components を使うアプリは、Server Action を 1 つも書いていなくても、RSC のリクエストを解釈する経路を持つ（2025 年 12 月の React2Shell / CVE-2025-55182 はこの解釈処理が突かれた）
- Livewire は、コンポーネントのプロパティ更新をクライアントから受け取る口を自動で持つ（2025 年に、その復元処理で RCE / CVE-2025-54068）
- Spring は、リクエストパラメータの名前から入れ子のプロパティまで自動で値を設定する（2022 年の Spring4Shell）
- 画像を受け取るだけのつもりのアップロードが、裏でメタデータ解析ツールに渡っていた（2021 年の GitLab / ExifTool）

どれも、開発者は「そんな入口を作った覚えがない」。この資料は、そういう受け口と解釈処理を拾うための手がかり。
**ここに書いた既定の挙動はバージョンで変わる。必ず対象のバージョンのコードと設定で確かめる。載っていない仕組みは、自分の知識とコードの読解で補う。**

## 1. 3 つの層で考える

| 層 | 問い | 例 |
|---|---|---|
| **入口**（経路） | どこに届くか | `POST /api/users`、WebSocket のイベント、キュー |
| **受け口**（入力チャネル） | その入口は、**何を** 入力として受け取るか。開発者が読んでいるつもりの項目以外に、何が読まれているか | 本文の形式（JSON だけのつもりが XML・multipart も通る）、ヘッダ、Cookie、クエリの構文、パスの構文、形式サフィックス |
| **解釈点**（パーサ） | 受け取った値は、**どの処理に解釈されるか** | デシリアライズ、XML、テンプレート、式言語、画像・文書の変換、URL 取得、アーカイブ展開、クエリ組み立て |

入口の一覧は「どこを叩くか」を、受け口と解釈点の一覧は「何を送ると何が動くか」を教える。診断対象として必要なのは両方。
受け口と解釈点は、1 つのルートに属するとは限らない。**アプリ全体・全ルート共通** で効くものが多く、それこそが見落とされる。

**受け口と解釈点の境目。** 基盤（フレームワーク・ミドルウェア・プロキシ・ランタイム）が、開発者のコードが動く前に値を受け取って形にする仕組みが受け口（A・B・C・E）。
特定の行で、値が解釈器に渡される呼び出しが解釈点（D）。同じ仕組みを両方に書くと別件として二重に残るので、どちらか一方に書く。
迷うもの（中継、キューのメッセージ、Server Action の引数、tRPC の入力、デバッグ用 UI、デバッガのポートなど）の決め方は、output-format.md の「受け口か解釈点か」の表にある。

## A. リクエスト処理の共通部分（全ルートに効く受け口）

各ソースについて、リクエストがハンドラに届く **前** と **外** で動くものを全部読む: ミドルウェア、フィルタ、インターセプタ、プラグイン、フレームワークの設定、サーバ／コンテナの設定。
それぞれ「何を読み、どう解釈し、どのルートに掛かるか」を記録する。

- **本文の解釈**: どの Content-Type を受けるか（JSON、フォーム、multipart、XML、テキスト、バイナリ）。全体に掛かるのか、ルート単位か。サイズ上限。圧縮された本文の展開。文字コード
- **クエリとフォームの構文**: 入れ子（`a[b]=c`）、配列（`a[]=1`、同名の繰り返し）、型の自動変換。文字列を期待する処理にオブジェクトや配列が届く形になっていないか
- **ファイルアップロード**: 特定のルートだけか、どのルートでも受けてしまうか。一時ファイルの置き場所。ファイル名・MIME の扱い
- **Cookie とセッション**: 署名・暗号化の方式、**中身のシリアライズ形式**（JSON か、言語固有の直列化か）、保存先
- **認証情報の読み取り**: どのヘッダ・Cookie・クエリから読むか（API キーをクエリでも受ける、など複数経路）。JWT のヘッダ項目（`alg` `kid` `jku` など）をどう扱うか
- **プロキシ由来のヘッダ**: `X-Forwarded-For` `X-Forwarded-Host` `X-Forwarded-Proto` `X-Real-IP` `Forwarded` などを信頼する設定。クライアント IP・ホスト名・スキームを使う処理（レート制限、URL 生成、アクセス制御）に効く
- **メソッドとパスの書き換え**: メソッド上書き（`_method`、`X-HTTP-Method-Override`）、パス上書き系ヘッダ、末尾スラッシュ・大文字小文字・エンコードされた区切り文字の扱い
- **形式の切り替え**: 拡張子（`.json` `.xml`）、`?format=`、`Accept` による応答・解釈の切り替え。ロケールやテーマの指定
- **CORS・CSRF・レート制限**: 判定に使う入力（`Origin`、トークンの受け取り場所、制限キーの元になるヘッダ）
- **エラー処理とログ**: エラーページや応答に入力が反映される箇所。ログに書かれる入力（ログ基盤側の解釈に届く）

## B. フレームワークが独自の形式で受ける口

画面やコンポーネントを書いただけで、フレームワークが専用の通信経路を作る。開発者はエンドポイントとして意識していない。
依存に次の種類の仕組みがあれば、**その経路と、そこで受け取って復元・実行されるもの** を載せる。

- サーバ側の関数やコンポーネントをクライアントから呼ぶ仕組み（React Server Components / Server Functions、Livewire、Blazor、Phoenix LiveView、Hotwire/Turbo、Inertia、htmx 連携、Vaadin、JSF、Wicket、Meteor など）
- コンポーネントの状態をクライアントに持たせて送り返させる仕組み（状態の復元 = デシリアライズ。ViewState、スナップショット、署名付きの状態）
- ページ用のデータ取得経路（データだけを返す別 URL、ペイロードファイル、アイランド／部分描画の経路）
- RPC 層（tRPC のバッチ、GraphQL のバッチ・GET クエリ・永続化クエリ、gRPC リフレクション、JSON-RPC の一括呼び出し）
- リアルタイム通信の制御メッセージ（購読・参加・コマンド。識別子が入れ子の JSON になっているもの）
- 開発・運用補助が持つ経路（ホットリロード、開発サーバのファイル配信、エラー画面の操作、プロファイラ）

これらは「ユーザー定義のハンドラが 0 件でも経路自体は存在する」ことがある。ハンドラの有無ではなく **仕組みが有効かどうか** で判断する。

## C. 自動バインドと自動クエリ

開発者が 1 項目ずつ読んでいなくても、リクエストの値が自動でオブジェクトやクエリに流れ込む仕組み。

- **オブジェクトへの自動バインド**: モデルバインド、データバインド、マスアサインメント。名前の一致だけで、想定外の項目（権限、所有者、金額、内部フラグ、入れ子のオブジェクト）に値が入る範囲
- **検索・絞り込み・並び替えの自動化**: クエリ文字列から任意の属性や関連をたどって検索・並び替えできるライブラリ、OData、JSON:API の `filter` `include` `fields`、GraphQL の自動生成フィルタ、ページングの件数指定
- **識別子として使われる入力**: 列名、テーブル名、並び順、関連名、クラス名、メソッド名、テンプレート名、ファイル名に入力が使われる箇所
- **ID の解決**: 文字列から任意の種類のオブジェクトを引ける仕組み（グローバル ID、多態的な参照）
- **データストアが構造を解釈するもの**: オブジェクトをそのまま条件に渡せるクエリ API（演算子として解釈される）、JSON パス、全文検索のクエリ構文

## D. 解釈点（パーサ・デシリアライザ・インタプリタ・変換器）

入口から辿るだけでなく、**解釈処理の側から逆に探す**。下の種類ごとにコード全体を検索し、見つけた処理に外部の値が届き得るかを遡る。
届く経路を確定できなくても載せる（`confidence: low`）。「ここには外から届かない」という思い込みこそが対象だから。

| 種類 | 探すもの（言語を問わず、該当する API・ライブラリ名で検索する） |
|---|---|
| デシリアライズ | 言語固有の直列化の復元、型情報つき JSON、YAML の完全ロード、メッセージ形式（MessagePack、Protobuf、Avro）、セッション・キャッシュ・ジョブの復元 |
| XML 系 | XML パーサ全般、SOAP、SAML、SVG、Office 文書、RSS / Atom、プロパティリスト、XSLT、外部実体・DTD の設定 |
| テンプレート・式 | 文字列からのテンプレート描画、式言語の評価、`eval` 相当、動的なコード生成、サンドボックス付き実行 |
| コマンド・クエリ | 外部コマンド実行（画像・動画・文書・Git・圧縮などのツール呼び出し）、生の SQL、NoSQL のクエリ、LDAP フィルタ、検索エンジンのクエリ |
| ファイル形式の解析・変換 | 画像（リサイズ、サムネイル、メタデータ）、動画・音声、PDF、Office、フォント、HTML→PDF／画像（ヘッドレスブラウザを含む）、OCR、バーコード |
| アーカイブ | zip・tar の展開、インポート用の束ねファイル、パッケージ形式、展開先のパス組み立て |
| 表・テキスト形式 | CSV、Excel、JSON、TOML、INI、Markdown、BBCode、HTML サニタイザ、リッチテキスト、メール（MIME）、vCard / iCalendar |
| URL・ネットワーク | 入力から組み立てた宛先への取得（プレビュー、取り込み、Webhook 送信、アバター取得、OIDC / SAML のメタデータ取得、フェデレーション）、URL の解釈、リダイレクト先 |
| パス・ファイル操作 | 入力を含むパスの組み立て、読み書き、インクルード、テンプレート選択、ストレージのキー |
| 認証トークン | JWT・SAML アサーション・署名付き URL・Webhook 署名の検証処理、鍵の取得元 |
| 正規表現・書式 | 入力から作る正規表現、書式文字列、ロケール依存の解釈、巨大入力・深い入れ子への耐性 |

**自動で走る解析に注意。** アップロード直後のウイルス検査・サムネイル生成・メタデータ抽出・全文索引、受信メールの解釈、リンクのプレビュー取得などは、
ユーザーの操作と離れた場所（ジョブ、コールバック、ライブラリ内部）で動く。入口のハンドラを読むだけでは見えない。

## E. プロトコルとインフラの層

アプリより手前で入力を解釈するもの。構成ファイルがあれば読む。無ければ「不明」と書く。

- リバースプロキシ・ゲートウェイ・CDN・WAF: ルーティングに使う項目（ホスト、パス、ヘッダ）、パスの正規化、ヘッダの追加・削除・信頼、キャッシュキー、画像変換などの付加機能、認証の委譲
- アプリとの解釈の食い違いが起きる箇所: パスの正規化、重複したヘッダやパラメータ、エンコード、本文の長さの決め方
- サーバレス基盤: イベントへの変換（ヘッダの多値、本文のエンコード、認証コンテキスト）、関数に直接届く別経路（関数 URL、他サービスからの起動）
- メッセージ基盤・ストレージ: メッセージやオブジェクトのメタデータを解釈する処理、署名付き URL のパラメータ
- 実行基盤そのもの: アプリサーバ／コンテナの既定のサーブレットやハンドラ、管理用プロトコル、セッション永続化

## F. スタック別の確認の起点

網羅ではない。対象のバージョンで実際にどうなっているかを、設定とコードで確かめるための出発点。

**Node / Express 系**
- 本文パーサ（`express.json` `express.urlencoded` `body-parser`）がどの形式を、アプリ全体に対して受けるか。`urlencoded` の `extended` とクエリ文字列は `a[b]=c` を入れ子のオブジェクトにする
- **登録の順序**: 全体に掛けた本文パーサは、個別のルートに付けた `express.raw` `express.text` より先に動く。先に本文を読み切られると、後ろのパーサには生の本文が届かない
  （Webhook の署名検証が生の本文を前提にしている場合に効かなくなる）。認証ミドルウェアとパーサのどちらが先かも、同じく登録順で決まる
- 既定のエラー処理（独自のエラーハンドラが無ければ、`NODE_ENV` が production 以外でスタックトレースを返す）。GET のルートは HEAD にも応答する
- `cookie-parser` は `j:` で始まる値を JSON として解釈する。署名付き Cookie、セッションの保存先と形式
- `trust proxy` の設定（`req.ip` `req.protocol` `req.hostname` の出どころ）、`method-override`
- multer の適用範囲（`.any()` や全体適用）、`express-fileupload` の設定
- Socket.IO / ws: 接続時のクエリ・ヘッダ・認証データ、メッセージ形式とサイズ上限
- GraphQL サーバ: バッチ、GET クエリ、永続化クエリ、introspection、アップロード用 multipart

**Next.js / React**
- App Router を使っていれば、RSC / Server Functions のリクエスト（専用ヘッダ、専用の Content-Type、multipart のペイロード）を解釈する経路がある。Server Action の定義数とは無関係
- ルーター用のクエリ・ヘッダ（`?_rsc=` など）、Middleware の内部用ヘッダ（`x-middleware-subrequest`、CVE-2025-29927）
- `/_next/image?url=`、`/_next/data/`、プレビュー／ドラフトモードの Cookie
- リダイレクトや URL 生成で `Host` / `X-Forwarded-Host` を使う箇所、API Routes の既定の本文パーサ

**Python（Django / DRF / Flask / FastAPI）**
- Django: `request.POST` / `request.FILES` に触れた時点で本文が解釈される（multipart は一時ファイルを作る）。`SECURE_PROXY_SSL_HEADER` `USE_X_FORWARDED_HOST`、セッションのシリアライザ、管理画面のクエリ文字列による絞り込み
- DRF: 既定のパーサは JSON・フォーム・multipart（`DEFAULT_PARSER_CLASSES`）。`?format=` と形式サフィックス。絞り込み・並び替え・検索で指定できる項目の範囲
- Flask: `get_json(force=True)`、`request.values`、署名付きセッション Cookie、ProxyFix
- FastAPI / Starlette: フォームとファイルの解釈ライブラリ、プロキシヘッダの扱い、型の自動変換
- タスクキューのメッセージのシリアライザ

**Ruby / Rails**
- パラメータの解釈（クエリ、フォーム、JSON、入れ子）、`_method` によるメソッド上書き、形式サフィックスと `Accept` による切り替え
- Cookie・セッションのシリアライザ、`request.remote_ip` が信頼するプロキシ、`config.hosts`
- Active Storage: アップロード後に自動で走るアナライザ／プレビューア（画像・動画・PDF を外部ツールで解釈）、variation の指定
- 検索ライブラリ（`q[...]` で指定できる属性・関連の範囲）、並び替え・ページングのパラメータ
- Action Cable のコマンド（識別子は JSON 文字列）、Turbo Stream、Action Mailbox のメール解釈
- グローバル ID の解決、`constantize` `send` `render` に外部の値が届く箇所

**PHP（素の PHP / Laravel / Symfony）**
- PHP 自体: どのスクリプトへの multipart でも、実行前にアップロードが一時ファイルになり `$_FILES` に入る。`php://input`、`$_REQUEST`、セッションの直列化、`unserialize`
- Laravel: `_method` によるメソッド偽装、信頼するプロキシ、ルートモデルバインディング、`$request->all()` と fillable / guarded、列名など識別子に使われる入力、暗号化 Cookie、キューのペイロード
- Livewire: 更新用の経路が、public プロパティの更新とメソッド呼び出しをクライアントから受ける
- Symfony: `_format` `_locale`、メソッド上書きの設定、信頼するプロキシ、Serializer が受ける形式、API Platform の形式ネゴシエーション

**Java（Spring / サーブレットコンテナ）**
- データバインド: `@ModelAttribute` や引数のオブジェクトは、パラメータ名から入れ子のプロパティまで設定される。`@InitBinder` の許可・禁止
- メッセージコンバータ: クラスパスにある形式が自動で有効になる（XML 用のライブラリがあれば JSON 向けの口が XML も受ける、など）。JSON ライブラリの多態型の設定
- multipart は既定で全体に有効。コンテンツネゴシエーション、マトリクス変数、パスの解釈（`;` 以降、末尾スラッシュ）、メソッド上書きフィルタ、forwarded ヘッダの方針
- Spring Data: ページングと並び替えのパラメータ、クエリ述語の自動バインド、プロジェクション
- 式言語（SpEL / OGNL / EL）に外部の値が届く箇所、ログに記録される入力
- コンテナ側: PUT や既定サーブレットの設定、セッション永続化、管理用コネクタ

**.NET**
- モデルバインド: ルート・クエリ・フォーム・本文・ヘッダから、公開プロパティすべてに値が入る
- 入力フォーマッタ（XML を追加していないか）、JSON ライブラリの型名処理
- forwarded ヘッダのミドルウェア、メソッド上書きミドルウェア
- SignalR: ハブの public メソッドはすべてクライアントから呼べる。Blazor: JavaScript から呼べるよう公開されたメソッド、回線上の UI イベント
- OData のクエリオプション、Razor Pages のハンドラ指定

**Go**
- `r.FormValue` / `r.ParseMultipartForm`: 呼んだ時点で本文全体を解釈する（multipart はメモリと一時ファイル）
- gin の `Bind` 系、echo の `Bind`: Content-Type に応じて複数の形式を受け、パス・クエリ・本文をまとめて構造体に入れる
- クライアント IP 取得が信頼するヘッダ
- `encoding/json`: キーの大文字小文字を区別しない、未知のフィールドを黙って無視する
- grpc-gateway: クエリパラメータがリクエストメッセージの各フィールドに自動で対応づく。メタデータ用ヘッダの受け渡し。gRPC リフレクション

**nginx / リバースプロキシ（アプリより手前の受け口）**
- `server` ブロックごとの `server_name` と `listen`（既定サーバはどれか。どのブロックにも当たらない Host がどこへ行くか）
- `location` ごとの転送先（`proxy_pass` の末尾スラッシュの有無で、上流に渡るパスが変わる）、正規表現の `location` と前方一致の優先順位
- **上流に渡るヘッダ**: `proxy_set_header` が 1 行も無ければ、クライアントが付けた `X-Forwarded-*` `X-Real-IP` や内部用ヘッダがそのまま上流へ届く。
  上流が信頼しているヘッダ（アプリの `trust proxy`、Middleware の内部ヘッダ）と突き合わせる。`Host` を何に書き換えているか
- `allow` / `deny`、`auth_basic`、`auth_request` がどの `location` に掛かり、どこに掛かっていないか（継承されない設定に注意）
- `client_max_body_size`、`merge_slashes`、`alias` と `root`（`location` の末尾スラッシュと `alias` の組み合わせ）、`autoindex`、`stub_status`
- 本番と検証で `server` ブロックが分かれているとき、片方だけ制限が外れていないか

## 追い方

2 方向から行い、突き合わせる。

1. **入口から前へ**: 各入口で受け取った値が、どの解釈点に届くかを辿る。ハンドラの中だけでなく、呼び出し先のサービス、ジョブ、コールバック、ライブラリの初期化設定まで
2. **解釈点から後ろへ**: D の種類ごとにコード全体を検索し、見つけた処理の入力が外部由来になり得るかを遡る

どちらか片方でしか見つからなかったものが要注意。入口から辿って届かない解釈点は「どこから届くか不明」と書いて載せ、
解釈点に届かない入口は「受け取った値がどこで使われるか未確認」と書く。

依存ライブラリの内部は読む対象にしていないが、**そのライブラリが何を受け取り何を解釈する役割か** は、依存の一覧と初期化コードから判断して載せる。
