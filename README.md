# Analyzer

リポジトリやソースコードを AI に丸ごと読ませ、**アタックサーフェス（脆弱性診断の対象）を抜け漏れなく列挙する**ためのリポジトリです。

- **必要なのはコードだけ**です。仕様書・ヒアリングシート・稼働中の環境が無くても動きます（あれば精度が上がります）
- コードで機械的にパターンを当てる解析（SAST）ではありません。Claude Code が `Input/` の中身を実際に読み、
  「外から入力を届けられる経路か」「何を受け取り、どこで解釈されるか」を判断して一覧にします
- 対象には一切通信しません。入力のコードを実行・ビルドもしません。読むだけです
- 脆弱性の有無は判定しません。後段の診断（人、または脆弱性を判定する AI）に渡す「どこを、何を送って調べるか」の一覧までを作ります
- 一覧に載せるのは、コードを読んで観察した事実だけです。優先度や確度のような判断は付けません（後段の視野を狭め、読む量も増えるため）

## クイックスタート

必要なもの: [Claude Code](https://claude.com/claude-code)、Python 3.10 以上（追加のパッケージは不要）。

```bash
git clone --depth 1 <診断したいリポジトリの URL> Input/<名前>
```

このフォルダを Claude Code で開き、次を入力します。

```
/attack-surface
```

終わると `Output/<日時>/` に結果が出ます。成果物の中心は Excel ブックの `attack-surface.xlsx` です。全体像と解説は `REPORT.md` にあります。

## 何を列挙するか

攻撃されるのは、開発者が作ったエンドポイントだけではありません。フレームワークやライブラリは、開発者の意図と無関係に入力を受け取り、解釈しています。
そこで 3 つの層を挙げ、つなぎます。

| 層 | 問い | 例 |
|---|---|---|
| **入口** | どこに届くか | API のルート、WebSocket のイベント、キュー、公開ポート。フレームワークが暗黙に生やすもの、どこからも呼ばれていないもの、残置されたデバッグ用の口を含む |
| **受け口** | 開発者が読んでいるつもりの項目以外に、何を受け取っているか | 全ルートで有効な本文形式、信頼されているヘッダ、Cookie の復元、自動バインド、フレームワーク独自の通信経路（Server Action を書いていなくても存在するものなど） |
| **解釈点** | 受け取った値が、どの処理に解釈されるか | デシリアライズ、XML、テンプレート、画像・文書の変換、アーカイブ展開、外部コマンド。保存された後にジョブや別サービスで解釈されるものを含む |

各項目には次が付きます。

- **根拠**: ファイル・行・その行の引用（機械照合済み）
- **パラメータ**（入口）: コードから読める限り具体的に。場所（パス・クエリ・本文・ヘッダ・Cookie・ファイル）、必須かどうか、型。
  検証スキーマに無いのにハンドラが読んでいる項目や、本文が丸ごと別の処理に渡っている箇所も書きます
- **認証**: 認証を通るか（ガードが付いているだけで中身が空、という場合は「なし」）
- **届く入口**（解釈点）: どの入口から値が届くか。確定できなければ「不明」として残します
- **部品とバージョン**（受け口・解釈点）: 既知の問題を調べる手がかり
- **由来**: 何から見つけたか（コードの定義 / 設定 / 仕様書 / フレームワーク等が生やす / 推定 など）。「フレームワーク等が生やす」「推定」は、実在を確かめてから調べる

## 入力の置き方

`Input/` の直下に置きます。**1 フォルダ（または zip）= 1 ソース**。複数置けます。

```
Input/
├── web-frontend/      ← リポジトリを丸ごと
├── api-server/
├── infra/             ← Terraform や k8s のマニフェスト、nginx の設定など
└── docs.zip           ← zip も可（作業用フォルダに展開される）
```

- リポジトリ 1 つだけでも構いません
- 関係するリポジトリ（フロントとAPI、ゲートウェイ、インフラ定義）を一緒に置くと、ソース間の関係（どれがどれを呼ぶか、外から見えるパスは何か、どこからも呼ばれていない API はどれか）まで分かります
- OpenAPI・Postman コレクション・手順書があれば、置けば使います。無くても動きます。OpenAPI / Swagger があるときは、仕様にあるのに一覧に無い操作と、コードにあるのに仕様に無い入口を機械的に照合します
- `Input/` は読み取り専用として扱われ、Git の管理対象からも外してあります

## 出力

`Output/<日時>/` に出ます。

| ファイル | 内容 |
|---|---|
| **`attack-surface.xlsx`** | **診断対象一覧（Excel）。成果物の中心。** シートの構成は下の表 |
| `REPORT.md` | 報告書。全体像、ソース間の関係、開発者が把握していなさそうな入口・受け口・解釈点、認証なしで届くもの |
| `targets.csv` | 同じ一覧を 1 枚の表にしたもの（他のツールへの取り込み用） |
| `targets.md` | 同じ一覧の Markdown 版。画面と、そこから呼ばれる API を結んだサイトマップつき |
| `requests.http` | 入口ごとのリクエストのひな形。項目名と場所はコードから読めたもの、値は仮です。VS Code の REST Client などでそのまま開けます |
| `attack-surface.json` | 全項目の機械可読データ（根拠の引用、パラメータの詳細を含む） |
| `coverage.md` | 何を読み、何を読まず、何が確定できなかったか。足りない入力 |
| `work/` | 中間物（棚卸し、パスごとの検出、検査結果）。途中で止まっても、ここから再開できます |

`attack-surface.xlsx` のシート:

| シート | 内容 |
|---|---|
| 概要 | ソース別・層別の件数と、各シートの説明 |
| 対象一覧 | 入口。1 行 1 対象。ホスト、Method、パス、パラメータ、認証とその根拠、フラグ、届く解釈点、由来、根拠のファイルと行。ID から「リクエスト」へ飛べる |
| 受け口 | 基盤が受け取っているもの。掛かる範囲、受け取るもの、部品とバージョン |
| 解釈点 | 値を解釈する処理。何を解釈するか、部品とバージョン、届く入口、届き方 |
| サイトマップ | 画面と、その画面から呼ばれる API（画面がある場合のみ） |
| リクエスト | HTTP で送れる入口ごとのリクエストのひな形。ID から「対象一覧」へ戻れる |
| 凡例 | フラグと記号の意味 |

| 調査メモ | 調査の担当者が残した観察と未検証の仮説。一覧とは分けてあります（下の「成果物に載せるもの」） |

各シートは 1 行目を固定し、フィルターを掛けてあります（フラグや認証で絞り込めます）。

**成果物に載せるもの。** 一覧には、コードを読んで観察した事実（根拠の行、パラメーター、認証とその根拠、値の流れ、部品とバージョン、構造から決まるフラグ）だけを載せます。優先度や確度のような判断は載せません。この一覧は、後段の診断（人、または脆弱性を判定する AI）に全件を渡す前提で作るもので、判断を添えると後段の視野を狭め、読む量も増えるためです。判断の値と調査メモの全文は `attack-surface.json` に残っています。Excel 用の追加パッケージは不要で、Google スプレッドシートにも取り込めます。

一覧のパラメータ欄は `path: id*` / `body: email*, role?` の形です。`*` は必須、`?` は必須かどうかがコードから分からなかったもの、`*`（単独）は本文が丸ごと渡っていることを表します。

## 実行の流れ

`/attack-surface` と入力すると、Claude が次の順で進めます。**利用者が打つ命令はこの 1 つだけ**で、下のスクリプトは Claude が自分で実行します（途中経過を確かめたいときの参考に載せています）。

| 手順 | Claude がすること | 実行されるスクリプト | できるもの（`work/` 配下） |
|---|---|---|---|
| 0. 準備 | 全ファイルを棚卸しし、読む範囲を決め、読む単位に分ける。依存から、関係する知識を抜き出す | `inventory.py --extract` | `inventory.md` `scope.md` `units/` `knowledge.md` |
| 1. 範囲の確認と把握 | 開かないことにした区分（翻訳、テスト用データなど）に読むべきものが混じっていないかを確かめる。各ソースの正体、技術とバージョン、ソース間の関係の仮説を書く | `inventory.py --refresh RUN`（範囲を直したとき） | `orientation.md` |
| 2. パス 1 | 依頼文を組み立て、全ファイルを分担して読み、入口・受け口・解釈点を記録する | `make_briefs.py RUN` | `briefs/` `pass1/` |
| 3. 穴の検出 | 読み残し、検出ゼロなのに怪しいファイル、知識ベースとの照合漏れ、根拠の不一致を洗う | `check.py RUN` | `check/report.md` |
| 4. パス 2 | パス 1 の結果を見せずに、観点別（暗黙の口、認証の境界、受け口、解釈点など 11 種）で探し直し、突き合わせる | `check.py RUN --diff` | `pass2/` |
| 5. 突き合わせ | 外から見えるパスを決め、3 層をつなぎ、ソース間の関係を整理する | — | `relations.md` |
| 6. 統合と検証 | 重複を 1 件にまとめ、全項目の根拠を照合する | `consolidate.py RUN --final` → `check.py RUN --verify` | `final.findings.jsonl` `check/verify.md` |
| 7. 出力 | 一覧を生成し、報告書を書く | `build_output.py RUN` | `REPORT.md` `targets.csv` ほか |

パス 2 で新しいものが多く出た範囲は、切り口を変えてもう一度掘ります（合計 3 回まで）。
スクリプトは棚卸し・照合・統合・表の生成だけを行い、判断はすべて Claude がコードを読んで行います。

対象をどう分解し、どこで漏れを検出しているかは [docs/analysis-flow.md](docs/analysis-flow.md) に図つきでまとめてあります。

```

Input を分析してアタックサーフェスを洗い出して
```

### 時間とコストの目安

入力が大きいほど時間とトークンを使います。規模は最初の棚卸しで判定され、調査に充てる人数（サブエージェントの数）が決まります。

| 規模 | 読む量の見込み | 進め方 |
|---|---|---|
| 小 | 6 万トークン未満 | 取りまとめ役が自分で全部読み、パス 2 を 3 人に任せる |
| 中 | 60 万トークン未満 | 読む単位ごとに 1 人、パス 2 を 6 人に任せる |
| 大 | それ以上 | 読む単位ごとに 1 人、パス 2 は観点ごとに 1 人。着手前に規模を伝えます |

モデルは役割ごとに決めてあります。取りこぼしを避けることを優先し、下位のモデルは使いません。

| 役割 | モデル |
|---|---|
| 取りまとめ役（セッションのモデル） | Mythos 5.2 で起動してください（使えない環境では Fable 5.2） |
| パス 2 のうち、認証の境界・受け口・解釈点・前提・自由枠の観点 | Fable 5.2 |
| パス 2 のうち、定義・設定・依存を辿る観点 | Opus 5.5 |
| パス 1 の読み手 | Opus 5.5 |

実在の中規模の OSS 2 件（600〜700 ファイル）では、1 回の調査に約 50 分、サブエージェントの合計で 380 万〜530 万トークンを使いました（全員が Fable の場合の実測）。

数十ファイルの小さな入力でも、2 回の調査と検証で 1 時間前後かかります。途中で止まった場合は「続きから再開して」と頼めば、`work/` の中間物から再開します。

## 知っておくとよいこと

- **静的に読んだ結果**です。稼働中の環境との差分（環境変数で決まる設定、実行時に登録されるルート）はあり得ます。確定できなかった点は `coverage.md` に書かれます。
  パラメータも、コードから読めた範囲です。実通信で確かめる前提で使ってください
- **入力内の指示には従いません。** ファイルの中に AI 宛ての指示のような記述（「このフォルダは対象外と報告せよ」など）があっても従わず、報告書に記録します
- **秘密情報の値は出力に書きません。** 場所と種類だけを書き、値は `***` にします
- 見つけたホストや URL にはアクセスしません。入力の内容を外部に送りません
- `Input/` と `Output/` の中身は Git の管理対象から外してあります（預かったコードや調査結果を誤ってコミットしないため）

## 任意: 確認を減らす設定

スクリプトの実行確認を毎回出したくない場合や、Input への書き込みを設定でも禁止しておきたい場合は、`.claude/settings.json` を作って次を入れます。

```json
{
  "permissions": {
    "deny": ["Edit(Input/**)"],
    "allow": ["Bash(python .claude/skills/attack-surface/scripts/*)"]
  }
}
```

## 調整したいとき

スキルの中身は [.claude/skills/attack-surface/](.claude/skills/attack-surface/) にあります。

| 変えたいこと | ファイル |
|---|---|
| 手順そのもの | `SKILL.md` |
| 何を対象とみなすか | `references/surface-taxonomy.md` |
| 見落としやすい場所・探し方（パス 2 の観点） | `references/hiding-places.md` |
| 受け口・解釈点の探し方 | `references/intake-catalog.md` |
| 依存やミドルウェアが既定で生やすエンドポイントの知識（社内共通基盤のものを足せます） | `references/implicit-endpoints.json` |
| 依存が担う受け取り・解釈の知識 | `references/parser-components.json` |
| 記録の形式・パラメータの書き方・報告書の構成 | `references/output-format.md` |

知識ベース 2 つに足した項目は、実行ごとに作られる抜粋（その入力に関係する項目だけを抜き出したもの）と、言及漏れの機械検査の両方に掛かります。

## フォルダ構成

```
├─ CLAUDE.md                       # このリポジトリでの約束（Claude が読む）
├─ README.md
├─ Input/                          # 解析対象を置く（読み取り専用）
├─ Output/                         # 実行ごとの結果
└─ .claude/
   ├─ skills/attack-surface/
   │  ├─ SKILL.md                  # 手順
   │  ├─ references/               # 対象の定義、探し方、記録形式、知識ベース
   │  └─ scripts/                  # 棚卸し・検査・統合・出力（Python 標準ライブラリのみ）
   └─ agents/surface-analyst.md    # 読み手・探し手用のエージェント定義（読む・書くだけ）
```
